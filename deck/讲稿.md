## 01 · 机器人看到台阶后，数据去了哪里？

一条主线：测量 → 对齐 → 表示 → 决策 → 动作

1. **测量**：眼睛看到距离，身体感觉到运动。
2. **对齐**：把不同时间、不同方向的测量，放进同一个参考系。
3. **理解**：保留任务需要的形状与状态，压成一组数字。
4. **行动**：控制器不断读这些数字，更新电机动作。

讲解补充：本演讲解释数据通路，不做算法排行榜。示意动画的机器人、地形与点数量不代表真实实验。按P播放/暂停，J/K逐步，方向键翻页，N查看讲稿。每页自动演示一轮后停住。

## 02 · 三个传感器，送来三种“语言”

下面是统一教学配置，不是所有设备的固定规格。

1. **IMU**：200次/秒，每次6个数：3轴角速度 + 3轴加速度。
2. **深度相机**：20张/秒；示例一张640×480，每个像素存一个距离。
3. **激光雷达**：10包/秒；每包N个点，N会变化，每点含XYZ和采集时间。
4. **共同问题**：它们既不同步，也不是同一种数，不能直接求平均。

讲解补充：IMU示例每5ms一条；深度每50ms一张，307200个深度值；点云每100ms一包，N可变。这些是教学配置，不是D435i/Mid360本地仿真配置。RGB另有颜色通道；深度不是RGB图片，也不是imu。数据量为元素数量，非网络字节率。

## 03 · 更相信误差小的那条消息

只融合“同一时刻、同一位置量”的两个估计。

1. **旧估计**：我原来估计位置是0米，误差方差是4。
2. **新测量**：新测量说是2米；测量方差越小，越值得信任。
3. **加权修正**：默认测量方差1：向测量移动80%，得到1.6米。
4. **更有把握**：融合后的方差变成0.8，位置范围比原来更集中。

讲解补充：一维线性高斯、预测误差与观测噪声独立的教学例子。预测均值0，P=4；测量z=2，R默认1；K=P/(P+R)=0.8；后验均值1.6，方差(1-K)P=0.8。图中的曲线由真实高斯密度公式计算，滑块改变R并重新计算，不是实测。这里的权重不是一般情况下对原始像素和IMU做平均。

## 04 · 边走边猜，看到新证据再纠正

预测让估计继续前进；测量让误差收回来。

1. **起点**：刚校正过，位置估计范围较窄。
2. **预测**：运动一段时间，预测前进；不确定范围变宽。
3. **观测**：相机或雷达提供与当前状态对应的新证据。
4. **校正**：根据可信度修正位置，继续下一轮预测。

讲解补充：动画位置、范围为教学示意，不是用IMU单个加速度样本直接得到绝对位置。真实惯性估计积分角速度与比力，并处理重力、偏置和协方差；视觉重投影或点面残差通过测量模型修正状态。下一页说明测量的采集时刻。

## 05 · 快的数据一直跑，慢的数据到了再更新

教学时钟：IMU 200 Hz，相机20 Hz，点云10 Hz。

1. **0–45 ms**：每隔5毫秒，IMU推动一次状态预测。
2. **50 ms**：相机有了新图像，先对齐到50毫秒，再校正状态。
3. **55–95 ms**：IMU继续预测；控制器仍可读取最新估计。
4. **100 ms**：相机与点云到更新时刻；按各自观测模型处理。

讲解补充：100ms为教学窗口。异步融合不要求所有传感器同频。按采集时刻而非网络到达时刻；迟到观测需历史缓存/平滑与重传播。100ms同刻观测可按系统设计更新，不表示任意非线性算法顺序都等价。控制器读取估计的频率与传感器频率是不同概念。

## 06 · 深度图中的一个像素，变成空间中的一个点

距离图 → 相机坐标XYZ → 机器人坐标XYZ。

1. **距离图**：深度图不是照片：每个有效格子存一个距离。
2. **变成点**：结合相机内参，把“哪个像素 + 多远”变成XYZ。
3. **对齐方向**：用安装位置和姿态，把相机点与雷达点转到同一坐标系。
4. **对齐时间**：历史点再根据机器人运动补偿到当前时刻，才能合在一起。

讲解补充：光轴深度d反投影为p=d K^-1[u,v,1]。真实点云有逐点时间，运动补偿需要轨迹。图中9×6缩略格与点数只供看清机制。本地仿真射线直接返回世界坐标命中点，真实相机反投影和扫描去畸变是部署时需要的接口，不声称已有实机驱动。

## 07 · IMU先猜姿态，点云再对齐墙面

一大包点 → 几何误差 → 位置、姿态、速度与可信范围。

1. **IMU预测**：角速度和加速度，先把运动状态推到新时刻。
2. **扫描补偿**：按运动估计，把一包点的不同采集时刻对齐。
3. **几何校正**：点与已有局部地图的表面对齐，误差帮助修正运动状态。
4. **共享状态**：状态既用于控制，也用于把历史感知放回正确位置。

讲解补充：以FAST-LIO2类LIO解释机制，不宣称复现算法。点面残差经滤波更新状态；系统内部局部地图为配准服务，不等于全局任务路线地图。本页不指定统一频率与固定状态维数，设备、配置、算法扩展均会影响它们。

## 08 · “我在哪”与“脚怎么踩”，需要不同的数据

定位结果支撑感知对齐；任务还需要周围形状。

1. **定位**：融合IMU与几何观测，得到身体的位置和姿态。
2. **看地形**：把可见点压成局部高度、有效标记和短时记忆。
3. **选方向**：导航给出目标方向或速度指令。
4. **落到动作**：运动策略把指令、地形和身体状态变成关节目标。

讲解补充：本页是通用分层工程架构，不声称当前高台技能已经接入任意目标导航。状态融合与特征融合不是同一个优化步骤；神经网络内部拼接特征也不等于做卡尔曼更新。

## 09 · 先看清：本地实验每100毫秒收到什么

Rob2Nav perceptive_rl：简化传感器仿真，不是实机扫描。

1. **深度返回**：32×20 = 640条相机射线；每100毫秒更新一次。
2. **雷达返回**：96×12 = 1152条雷达射线；每100毫秒更新一次。
3. **合并可见点**：最多1792条射线返回；遮挡、未命中和丢点会减少有效点。
4. **任务信息**：台沿、台面和缺失区进入局部地形；近脚下主要依靠下倾相机。

讲解补充：来自本地perceptive_rl/sensors.py：相机下倾20度，4m量程；雷达水平360度、多仰角-7至52度，8m量程；两者10Hz。射线数量是发射方向数，不能称为1792个有效三维点，更不能当作真实硬件数据率。仿真没有完整RealSense成像或Livox扫描模型。

## 10 · 一堆点，压成187个“地形小格”

17×11局部格：每格高度 + 是否真的看见。

1. **点落入格子**：把可见点放进机器人附近的10厘米格子。
2. **保留高度**：同格保留最高有效返回，压成187个相对高度值。
3. **标明未知**：再加187个有效标记：0表示未知，不表示平地。
4. **带上记忆**：已见点最多保留1秒，随运动重投影；过期清除。

讲解补充：perceptive_rl/elevation.py为17×11、10cm网格，取格内最高命中点，保存实际世界坐标与时间；当前实现使用理想仿真位姿。高度输入实际为机体z减格点z再减0.5，并裁剪到[-1,1]。未知高度填0而掩码为0。初版419维输入没有年龄通道；后续MoE使用33×21×3高度/掩码/年龄，本讲不混合这两版。

## 11 · 374个地形数 + 45个身体数 → 12个动作

每20毫秒运行一次：419 → 512 → 256 → 128 → 12。

1. **地形374**：187个高度 + 187个有效标记。
2. **身体45**：转动、重力、指令、关节角/速度、上一动作，共45个数。
3. **网络419**：拼成419维输入；中间层逐步混合地形与身体信息。
4. **动作12**：输出12个关节偏移，转成关节目标，再由PD跟踪。

讲解补充：45=角速度3+投影重力3+速度指令3+关节位置12+关节速度12+上一动作12。MLP隐藏层512/256/128，ELU。419是元素数，不是维度已学会的语义；中间神经元并不一一对应“台高”“抬腿”。关节目标q_default+0.25*a；PD把位置/速度误差转为力矩。PhysX步长5ms，对应200Hz物理/PD执行；策略50Hz。

## 12 · 老师先学动作，学生再学怎样看

训练会更新网络参数；部署时只运行学生。

1. **教师练习**：理想地形 + 身体状态 → 教师动作 → 仿真环境与奖励。
2. **学生模仿**：同一个状态：学生看可见地形，教师给12维动作标签。
3. **学生强化**：学生亲自执行；保存观测、动作、奖励，PPO继续更新参数。
4. **部署推理**：移除教师与价值评估网络，只保留传感器、学生和控制器。

讲解补充：本地教师232或235维，学生419维。教师PPO的特权高度来自仿真真值，并非提前扫描实景。蒸馏是动作MSE监督学习，混合roll-in转向学生访问状态；随后学生PPO用交互序列(o,a,r,done,logprob,value)更新。训练critic可看理想地形和真实速度，部署不保留critic。数百轮训练记录与结果留在研究材料，不占科普主讲。

## 13 · 100毫秒里，看一次，动五次

本地仿真：感知10 Hz；策略50 Hz；物理/PD 200 Hz。

1. **0 ms**：新感知更新地形缓存；策略读地形 + 当前身体状态。
2. **20 / 40 ms**：没有新扫描；重投影已有记忆，结合新身体状态再算动作。
3. **60 / 80 ms**：继续更新关节目标；每5毫秒的PD跟踪最新目标。
4. **100 ms**：下一批感知到来，重新更新地形；循环继续。

讲解补充：计数窗口[0,100)ms为1次感知、5次策略、20次物理/PD；100ms属于下一周期。示意忽略计算耗时与传输延迟，不代表实机端到端延迟为0。无新点也可随位姿重投影并清除旧记忆，因此不是原封不动地复读全部419维。策略每次都结合最新身体观测。

## 14 · 也可以把深度图，直接压成一个特征向量

Extreme Parkour：用视觉特征替代教师的理想地形表征。

1. **深度图**：论文预处理后58×87，共5046个深度值。
2. **视觉编码**：CNN提取空间特征，GRU带上历史；视觉分支约10 Hz。
3. **特征融合**：视觉特征与本体观测汇合，运动策略约50 Hz。
4. **运动动作**：输出关节指令；训练用教师监督动作与航向。

讲解补充：Extreme Parkour论文III-B/C及IV-A。58×87深度→CNN/GRU视觉表征/航向→运动策略→关节命令。论文相机采集10±2Hz，视觉骨干10Hz、策略50Hz；固定从接收图像到发送特征的延迟80ms，身体观测延迟16ms。由此说明“用最新可用特征”并不等于没有延迟。压缩特征维数不在本讲固定，避免不同代码版本混用。局部格是人为设计的表示，latent是学习得到的表示，两者都使高维感知进入动作网络。

## 15 · 地图可以教导航，却不必跟着学生上场

先问：它提供动作答案，还是只提供训练评分？

1. **全局几何**：训练场景知道障碍、起点与目标；能算绕障路径。
2. **两种教法**：一条路给专家动作；另一条路只按绕障进度和安全距离打分。
3. **局部学生**：学生部署仍只看局部传感器、身体状态和目标。
4. **边界**：导航在线不读全局地图，也可能有局部记忆和定位模块。

讲解补充：通用架构示意。动作教师、特权critic、地图奖励和在线规划地图是不同用途。本地高台教师不是导航地图教师。Safety-Shielded RL用Dijkstra路径势场及ESDF计算训练奖励，不能据此说它通过地图教师蒸馏动作。地图辅助训练不保证学生能解决任意未见死胡同。

## 16 · 会迈腿以后，还要决定往哪里走

导航的四个接口：我在哪 → 去哪里 → 怎么绕 → 怎样执行。

1. **定位**：把点云放进稳定的坐标系，知道机器人当前在哪里。
2. **路线**：任务层给目标点或参考路径；一条路线可以跨多个局部地图。
3. **轨迹**：局部规划结合机身尺寸和障碍，生成下一段可执行运动。
4. **执行**：跟踪器产生速度指令，底层运动控制器负责关节与平衡。

讲解补充：接续前面的运动策略：运动能力不等于目标导航。后面用LIO解释定位接口、SCAN解释几何规划、VbotNav解释云边任务分工。四个模块可以替换，但坐标、时间戳、输出类型和失效行为必须保持契约。

## 17 · 先算清“我在哪”，点云才能对齐

LiDAR-Inertial Odometry：雷达—惯性里程计，为SCAN提供可靠位姿。

1. **预测**：IMU先预测姿态、速度和位置，填补两帧雷达之间的运动。
2. **去畸变**：用逐点时间和运动轨迹，把同一扫描中的点对齐。
3. **校正**：将点云与局部地图配准，用几何残差修正状态和IMU偏置。
4. **交给SCAN**：输出带时间戳的位姿与点云；SCAN据此建立局部障碍地图。

讲解补充：SCAN关联定位项目是Elevator-LIO，源于FAST-LIO2路线。定位内部地图用于配准，SCAN占据地图用于碰撞判断，两者目的不同。可靠位姿是必要接口，但并非只能使用LIO；其他定位系统也可替换。你此前遇到的IMU覆盖不足应先解决，不能通过伪造时间戳或扩大队列掩盖。本文未执行真机修复。

## 18 · SCAN：把目标变成绕开障碍的轨迹

点云 + 位姿 + 目标/路径 → 局部地图 → B-spline → 速度指令。

1. **输入**：PointCloud2描述障碍；Odometry描述机身和传感器位姿。
2. **规划**：双圆柱考虑机身朝向，投影A*提供绕障引导，B-spline优化轨迹。
3. **输出**：发布 /planning/bspline；闭环跟踪器再输出 cmd_vel。
4. **真机接入**：Go2还需速度门与SDK执行层；SCAN本身不生成关节步态。

## 19 · SCAN主要吃几何计算与地图内存

论文实机：Jetson Orin NX；这不是最低芯片要求，也不是纯GPU任务。

1. **计算位置**：LIO、点云融合、A*和优化需要机载计算；主规划路径主要是CPU工作。
2. **地图规模**：默认10×10×5米、5厘米体素，对应400万个体素。
3. **内存预算**：七个体素数组约76 MB；整套进程还要加LIO、点云、搜索和ROS。
4. **测量验收**：实测延迟与峰值RAM；5厘米改2.5厘米，同体积体素内存约增8倍。

讲解补充：论文实机所有模块运行于Orin NX，仿真CPU为i9-14900K，不能混写。76MB来自源码常见ABI：8+1+4+2+2+1+1=19B/体素，乘4百万；仅七个数组，不含A*、点云、LIO地图和RViz，不是整机RAM最低值。GPU仿真渲染选项不等于规划器要求CUDA。原文没有给通用最低RAM/TOPS/传感器带宽；验收需记录全链路p95/p99延迟、内存峰值与温控。

## 20 · VbotNav：云端想方向，机载持续避障

云端产生子目标；机载用最新RGB与LiDAR，持续重算局部轨迹。

1. **云端输入**：图像历史 + 导航指令 + 参考路线，交给4B云端策略。
2. **云端输出**：输出子目标指导；不是给机器人下载新网络权重。
3. **机载输出**：RGB与LiDAR融合后生成10点轨迹，再交给独立运动控制器。
4. **异步协作**：云端结果未到时，机载沿用有效指导；过期与断连由监督层处理。

讲解补充：论文标称2Hz云端、10Hz机载、50Hz运动控制，并非端到端延迟实测。每个轨迹点为(x,y,sinψ,cosψ)。室内依赖提前规划的参考路线，不能当成开箱即用的未知环境探索。公开检索找到VitaDynamics/vbot-lab开发工具和vbot_ros2_msgs接口，尚未找到VbotNav完整模型代码/权重；团队工具仓库不是论文实现。

## 21 · VbotNav的算力，要按云端与机载分账

已知模型结构，不等于已知最低芯片、显存与上行网络规格。

1. **云端权重**：4B模型若用FP16/BF16，仅权重约8 GB；运行时需求更高。
2. **机载计算**：视觉编码 + LiDAR BEV + 轨迹网络，适合评估GPU推理与加速。
3. **时限预算**：标称10Hz机载循环对应100ms周期；须测完整链路，不能只测网络前向。
4. **尚未披露**：完整芯片、峰值RAM/显存、网络码率未明确；不能据此承诺某板卡可跑。

讲解补充：8GB为4×10^9参数×2字节的十进制算术下界，不含视觉分支额外开销、KV缓存、激活、框架或并发；不是部署容量建议。机载有DINOv3、DA2-Small、LiDAR BEV融合和flow-matching轨迹网络；没有完整权重和部署配置，不能给可靠TOPS、FPS或内存最低值。要记录输入大小、精度、推理引擎、p95/p99时延、功耗和网络条件。

## 22 · 带宽先看：跨网络的是图像，还是目标？

下面是可重算的教学载荷，不是任何论文的实测码率。

1. **原始相机**：640×480、RGB8、10Hz：约73.7 Mb/s；还没计算协议开销。
2. **深度与点云**：同尺寸16位深度约49.2 Mb/s；示例点云约25.6 Mb/s。
3. **压缩上传**：假设每张JPEG 100 kB、每秒2张，约1.6 Mb/s；实际取决于画面与编码。
4. **小量指导**：10点×4个float32×10Hz仅12.8 kb/s；云端频率不等于传感器上传频率。

讲解补充：十进制单位：RGB=640×480×3×10×8；深度=640×480×2×10×8；点云假设2万点/包、point_step=16B、10Hz，得到25.6Mb/s，不能当MID360规格。JPEG示例100kB×2×8=1.6Mb/s；历史多帧、多相机或重复上传会增加。轨迹载荷10×4×4×10×8=12800b/s；不是Vbot实测传输协议。公网需测延迟、抖动、丢包和重连；原始点云留机载可减轻网络负担。

## 23 · 点云压成“每个方向离障碍多远”

Flying on Point Clouds：局部感知 → 状态融合 → 推力与角速度。

1. **点云10 Hz**：历史点云对齐到当前机体系，保留有限历史。
2. **方向表示**：划成3200个球面角分区，保留距离与未知空间信息。
3. **融合状态**：感知表示与速度、姿态、目标、上一动作送入MLP。
4. **控制50 Hz**：每20毫秒给出推力与机体角速度，由飞控执行。

讲解补充：按Flying on Point Clouds v1 III-A与IV概括。3200是论文分区实例数，不将其写成原始点数或最终全部网络输入维数。通过局部状态估计对齐历史，避免显式占据栅格规划。训练仿真提供几何和交互反馈，在线不等于无状态估计或无记忆；飞行方向距离不能直接替代四足支撑高度。 论文机载使用Jetson Orin NX，估计与GPU推理在机载执行；没有给统一最低RAM。未确认2025这篇论文的独立代码库，不链接2018/2019同名pointcloudTraj。

## 25 · 让云端决定意图，让机载守住实时闭环

工程建议：可靠定位 → 局部避障 → 有保护的执行，最后再接语言导航。

1. **先定位**：MID360 + IMU → LIO；先验证时序、静止漂移、点云与TF一致性。
2. **再规划**：SCAN接收点云、位姿和目标，先完成低速、短距离、平地导航。
3. **接执行**：轨迹跟踪 → 速度门 → Unitree SDK；超时、失定位和急停在机载处理。
4. **最后上云**：云端下发带时间戳和坐标系的目标；机载检查有效性，再交给SCAN。

讲解补充：这是借鉴云边分工的工程组合，不是VbotNav原版复现。高飞团队两篇论文直接输出飞行动作；SCAN输出轨迹/速度；VbotNav分层输出子目标/轨迹，各自接口不能直接互换。无需为了云端语义推理把Go2 Noetic链整体改为ROS2。验收应覆盖过期目标、乱序结果、断网、定位掉线和控制权接管。

## 26 · 每到一个接口，问清楚四件事

什么形状？多久更新？表示什么？下一步拿它做什么？

1. **测量**：IMU的6个数、深度图的像素、雷达的XYZ点，是原始证据。
2. **对齐**：时间戳与运动状态，让不同传感器描述同一个时空。
3. **表示**：局部格、方向距离、神经特征：为任务保留有用的信息。
4. **行动**：闭环动作还要满足时效、算力、内存和带宽预算；接口失效时必须有明确行为。

讲解补充：本讲26页。主线从测量对齐、状态估计、局部表示与动作，延伸到LIO、SCAN和云边导航。论文硬件、代码推算、教学带宽例子分别标记；没有把配置频率当作延迟实测，也没有声称新增真机验证。
